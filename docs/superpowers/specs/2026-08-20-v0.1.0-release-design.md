# v0.1.0 Release Design

## Goal

Publish the first practical preview release of `go-minizinc`. The release adds
typed MiniZinc set and enum values, preserves warnings and checker output,
establishes automated compatibility checks, and documents the project license.

The work remains additive. Existing solve methods, options, result fields, and
minimum versions continue to work unchanged.

## Public Value Types

```go
type SetRange[T any] struct {
	Min T
	Max T
}

type Set[T any] struct {
	Elements []T
	Ranges   []SetRange[T]
}

type Enum struct {
	Value       string
	Constructor string
	Argument    any
}
```

`Set[T]` implements `json.Marshaler` and `json.Unmarshaler` for MiniZinc's JSON
set representation:

```json
{"set":[1,[3,5],8]}
```

Single values populate `Elements`; two-item arrays populate `Ranges`. Empty
sets are valid. Element order, duplicate values, and overlapping ranges are
not normalized because they do not change set membership.

`Enum` implements the same interfaces for all MiniZinc enum forms:

```json
{"e":"Canada"}
{"c":"C","e":{"e":"Canada"}}
{"c":"Right","e":2}
```

An atomic enum uses `Value`. A constructor uses `Constructor` and `Argument`;
its argument may be another `Enum` or a scalar accepted by MiniZinc. Marshal
and unmarshal operations reject missing values, conflicting forms, malformed
ranges, and unexpected object shapes.

Both types work directly in `Params` and as fields decoded through
`Result.Decode`. No separate parameter encoder or result decoder is added.

## Diagnostics

```go
type Warning struct {
	Message  string
	Location any
	Stack    []any
}

type CheckerMessage struct {
	Type         string
	Status       Status
	Output       map[string]any
	SectionOrder []string
	Statistics   map[string]any
	What         string
	Message      string
	Location     any
	Stack        []any
}
```

`Result` gains two fields:

```go
Warnings        []Warning
CheckerMessages []CheckerMessage
```

`Location` and stack entries remain `any` so the library preserves the exact
MiniZinc payload across supported versions instead of exposing a partial copy
of MiniZinc's evolving diagnostic schema. Checker messages expose the stable
JSON-stream fields and preserve their original order.

Warnings and nested messages from every checker event are accumulated during a
solve. They are attached once to the terminal result:

- `Solve` attaches them to its returned result.
- `SolveAll` attaches them to the last result, or to a synthetic terminal
  result when no solution exists.
- `SolveStream` attaches them to the final non-intermediate result, or emits a
  synthetic terminal result when needed.

This avoids repeating global diagnostics on every solution and keeps all
existing method signatures. MiniZinc error messages continue to produce
`*MinizincError`; warnings do not turn a successful solve into an error.

Maps and slices copied into public diagnostics are detached from the internal
stream messages. Existing raw solution output in `Result.Output` remains
available unchanged.

## Compatibility

The module continues to require Go 1.21 or newer and MiniZinc 2.6 or newer.
The new API is source-compatible with existing users and does not change JSON
encoding for existing Go values.

The set and enum encoders follow MiniZinc's documented JSON data format rather
than relying on a solver-specific representation. Diagnostics follow the
documented `warning` and `checker` JSON-stream message formats.

## Continuous Integration

Add `.github/workflows/ci.yml` for pushes to `main`, pull requests, and manual
runs. It uses least-privilege read permissions and cancels superseded runs.

The workflow contains focused jobs for:

- unit tests and `go vet` on Go 1.21 and the current stable Go release;
- `go test -race ./...` on the current stable Go release;
- `golangci-lint` through its pinned official GitHub Action;
- `go build ./...` for Linux amd64, Windows amd64, and Darwin arm64;
- integration tests against the minimum supported MiniZinc 2.6 release and
  the current stable MiniZinc release on Ubuntu.

MiniZinc integration uses official release bundles and verifies that the
required Gecode and COIN-BC solver paths are exercised. Action revisions and
tool versions are pinned in the implementation plan and updated deliberately.

## Release

Implementation is split into reviewable commits for value types, diagnostics,
project metadata, CI, and final documentation. Each commit passes its focused
tests before the complete suite is run.

After `main` passes GitHub Actions, create an annotated `v0.1.0` tag and a
GitHub Release. Release notes summarize the practical API, compatibility,
known preview status, and installation command without claiming v1 stability.

## Validation

Automated checks cover:

- set and enum JSON round trips, empty values, nested constructors, integer
  constructor arguments, malformed values, and use through `Params` and
  `Result.Decode`;
- warning and checker aggregation for `Solve`, `SolveAll`, and `SolveStream`,
  including no-solution terminal results;
- real MiniZinc set and enum input/output on supported versions;
- unit tests, race detection, vet, lint, examples, cross-platform builds, and
  the GitHub Actions workflow.

## Non-Goals

- No exported raw event stream or callback API.
- No immediate warning delivery during `SolveStream`.
- No generic algebraic data type for MiniZinc values.
- No normalization or set arithmetic helpers.
- No Builder DSL expansion.
- No v1 compatibility promise.
